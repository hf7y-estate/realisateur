# The estate at half its size, and the order to get there

Research pass for #1477. Every number below carries the command that produced
it, run from this container against the live GitHub org and a shallow clone of
each named repo (`gh repo clone hf7y-estate/<repo> -- --depth 1`). Host facts
beyond senechal#1083's read-only snapshot (quoted where used) are BLIND — this
container cannot reach `monkey`, `mandark`, `dexter` or `vaporwave` directly,
and two commands below (`bin/unarmed.sh`, `bin/registry-standup.sh`) proved
that the hard way by trying.

## Verdict, five lines

1. The estate already has the replacement it needs for scheduler's
   account/ROSTER dispatch model — realisateur's own `agent/nightly.sh` loop —
   and it has been running every night since at least 2026-09-28. The ~5,200
   lines of ROSTER/paced-runner machinery it replaced are still committed, 22
   of 26 ROSTER rows still point at the host that machinery calls `monkey`,
   and issue #1477's own brief calls that host deleted.
2. `bin/unarmed.sh`, run just now, returns 8 BLIND, 2 REGRESSED and 1 EXPIRED
   out of 11 rows — the floor that is supposed to catch exactly this is
   itself mostly unreadable, because 8 of its 11 remedies require reading
   `monkey`.
3. One of the two REGRESSED rows is a false alarm with a real cause:
   `registry-standup.sh` compares every repo's workflow text against
   `hf7y-estate/etalon/...`, but every calling workflow in the estate —
   including etalon's own canonical example — still says `hf7y/etalon/...`.
   The 2026-09-24 org rename (#672) was propagated into the checker's default
   but not into what it checks against, so it has reported 24-for-24 MISSING,
   falsely, for at least eleven days, and nothing reads its output on a clock.
4. Nothing blocks a merge on a red check anywhere sampled: `required_status_checks`
   is `null` on every branch-protected repo tried, and the rest can't even
   have branch protection on this GitHub plan. `agent/merge-carry.sh` already
   says so in its own comment, dated 2026-09-26, and it is still true today.
5. The estate's own diagnosis mechanism works — #954, #1388 and #1238 already
   found three of the five things this report found independently — but
   finding is not finishing: #954 has sat past its decision window for 18
   days, #1388's scoped deletion has filed zero of its sub-issues in the four
   days since it was scoped, and #1238's reap was abandoned mid-measurement
   with the backlog it measured now 19% larger than it was.

### 2b. A live bug the floor surfaced, not a dead one

`repo-frame` and `repo-guard` read REGRESSED above (was ARMED 2026-09-03,
20/20 and 20/20). Running the thing it calls directly, `bash
bin/registry-standup.sh` (2026-10-05), every one of 24 registered repos comes
back `MISSING .github/workflows calling hf7y-estate/etalon/.github/workflows/guard.yml`.
That is not a real regression. `grep -n GUARD_REF bin/registry-standup.sh`
shows `GUARD_REF="$OWNER/etalon/.github/workflows/guard.yml"` with
`OWNER="$GH_ESTATE_OWNER"`, which `bin/lib/estate-set.sh` defaults to
`hf7y-estate` (set there for #672, the 2026-09-24 org rename). But the actual
calling workflow — `grep -n etalon` on a shallow clone of senechal's
`.github/workflows/prose.yml` and `runtime.yml` — reads
`uses: hf7y/etalon/.github/workflows/guard.yml@main`, the **pre-rename**
owner, and etalon's own `canon/` copy of `guard.yml` prescribes that exact
string as the one every repo should paste in. `gh api repos/hf7y/etalon
--jq .full_name` resolves to `hf7y-estate/etalon` — GitHub's rename redirect
is carrying every one of these calls today — but `registry-standup.sh`
compares against the new name, which appears in zero live workflows, so it
can never match and has been reporting a false 24-for-24 failure since the
rename, eleven days ago by the time this ran. The only caller of
`registry-standup.sh` is `bin/unarmed.sh` itself (`grep -rn
registry-standup`), and nothing schedules `unarmed.sh --check` outside the
`unarmed-cadence` row that is itself BLIND above — so this has been silently
wrong, read by nobody, for the entire time it has been wrong.

This is worth fixing (one line: repoint `GUARD_REF` to the pre-rename owner,
or — better, since the redirect is not a thing to depend on forever —
actually move every calling workflow to `hf7y-estate/etalon` and then flip
`GUARD_REF` to match), but doing so is a code change to this repo and this
pass's own brief forbids that; it is reported, not fixed.

## 3. Layers one unattended change crosses, issue to merged PR

Read directly off `agent/nightly.sh`, `agent/run-agent.sh`,
`agent/merge-carry.sh` and this repo's own branch-protection state (this pass
*is* an instance of the thing being counted):

1. `dexter` cron, `0 1 * * * /srv/agent/nightly.sh` (per senechal#1083's
   snapshot).
2. `nightly.sh`: per-night flock, `gh repo list` for the candidate set,
   per-repo `queue_count()` (two more `gh`/`jq` calls), night budget.
3. `merge-carry.sh`, called *before* dispatch, to land the previous pass's
   PRs first.
4. `bin/etiquette.sh --apply`, to sync labels before the queue is read.
5. `run-agent.sh`: credential mint via `selfdev-gh-app.sh` (fresh token, no
   cache), `docker pull` by digest, then `docker run --rm` with a two-file
   mount.
6. Inside the container: `claude -p` with the brief above, `git clone --depth
   1`, branch, commit, `gh pr create`.
7. GitHub Actions on the PR: `tests.yml`, `branch-protection.yml`,
   `etiquette.yml`, `atteste.yml` — all informational; see §4, none required.
8. Next night's (or next sent run's) `merge-carry.sh`, the only place a merge
   decision actually gets made, reading `statusCheckRollup` itself rather
   than trusting required checks because there are none.
9. `estate-watch.sh --apply` on a separate `*/20` dexter cron, and
   `notify-senechal.sh`/`zaxon` for anything that needs a human.

Nine distinct mechanisms, each independently tested, for one issue to reach
`main` — and that is the realisateur side alone, before whatever the
*receiving* repo's own CI and reap tooling does to the same PR.
